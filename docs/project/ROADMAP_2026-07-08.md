# NXT Link — Project Audit and Execution Roadmap (2026-07-08)

This document is the single source of product truth. It supersedes earlier
status documents. Technical state lives in `TECH_HANDOFF_CURRENT.md`; the
core-transaction acceptance script lives in `CORE_TRANSACTION_TEST.md`.

## Executive decision

NXT Link is ONE private industrial sourcing marketplace, not a collection of
intelligence dashboards. The first sellable product is:

> Buyer describes a need -> NXT Link reviews and anonymizes it -> buyer
> approves the RFQ and vendor list -> selected vendors quote -> buyer compares
> quotes -> identity is revealed only after consent and required agreements ->
> NXT Link records its disclosed success fee.

Everything that does not make this transaction safer, faster, or easier is
secondary until this flow works end to end with real test accounts.

### P1 — complete one real transaction
- Buyer account and dashboard showing requests and status.
- Buyer edits and approves the exact anonymized RFQ packet.
- Buyer approves the exact vendor shortlist before outreach.
- Operator sends the RFQ only to selected vendors.
- Vendor sees only assigned opportunities; submits a structured quote.
- Buyer compares quotes side by side; requests revision or meeting.
- Consent, NDA/MNDA/NCA, and identity reveal enforced and logged.
- Both parties acknowledge the disclosed fee before introduction and before acceptance.
- Operator advances the deal through demo/pilot/selection/implementation/closed states.

### P1 — make the slice trustworthy
- Route-level authorization tests (buyer/vendor/admin).
- One Playwright end-to-end test covering the full transaction.
- Fix lint in core MVP routes first (Hooks violation in `src/app/vendor/quotes/page.tsx`).
- Stop skipping type/lint validation in production builds once MVP routes are clean.
- Test RLS directly: vendors must never read other vendors' quotes/leads/templates/documents.
- Test every identity-reveal and fee-acknowledgment failure case.
- Loading, empty, validation, recovery states on every core screen.

### P2 — launch operations
Notifications; operator action queue; vendor verification rules; legal terms +
professional review; support/dispute/data-retention procedures; funnel
metrics; bilingual human review of every core screen and email.

### P3 — after first successful transactions
Quote templates + PDF; AI brochure extraction w/ vendor approval; in-app
messaging; mobile operator intake; event matchmaking; reviews; payments,
e-signature, CRM, subscriptions, native apps.

## Paused until the first complete transaction works
Intelligence dashboards, world maps, signal feeds, new AI agents; new
industries/conference catalogs/data ingestion; more public pages or API
routes; payments/mobile/subscriptions/integrations; visual redesigns that do
not fix a core workflow problem.

## Four-sprint plan

1. **Staging and safety** — preserve work; identify staging/production; back
   up + reconcile staging DB; apply migrations safely; create three test
   personas; fix core-route lint blockers.
   *Exit:* all three personas sign in and access only their permitted records in staging.
2. **RFQ and quote** — buyer dashboard; persist anonymized RFQ packet; buyer
   packet + vendor-list approval; fan out only to selected vendors; structured
   vendor quote submission.
   *Exit:* one test buyer request reaches one test vendor, and the vendor
   returns a stored quote without learning protected identity data.
3. **Comparison, trust, and fee** — buyer comparison + revision/meeting;
   agreement/consent gates wired to reveal; fee disclosure + acknowledgments;
   audit history for approvals and stage changes.
   *Exit:* buyer can select a quote; every reveal/acknowledgment/stage change is auditable.
4. **Verification and pilot launch** — Playwright transaction test; authz +
   RLS tests; core notifications + operator queue; bilingual/accessibility
   review; concierge pilot.
   *Exit:* the full staging flow passes automatically; one real pilot runs
   without spreadsheets or hidden manual DB edits.

## Definition of MVP done
Buyer, vendor, operator complete the whole workflow in staging; buyer controls
what is sent and to whom; private data stays isolated; quotes compare and
revise; reveal/fee gates cannot be bypassed via UI or API; all consequential
actions logged; typecheck + unit tests + core lint + build + e2e pass;
legal/fee language professionally reviewed; one concierge pilot completed with
documented feedback.

## Weekly rhythm
One board: Backlog -> This Sprint -> In Progress -> Needs Review -> Verified -> Done.
Max three items in progress. Every item names user, visible outcome,
acceptance test, owner. "Code exists" is not done; "verified in staging with
the correct persona" is done. Weekly five-line report: shipped, verified,
blocked, decisions needed, next three priorities.
